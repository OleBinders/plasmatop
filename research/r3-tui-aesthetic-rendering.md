# R3 — TUI-aesthetic rendering spike

Question: what's the cheapest, most maintainable QML technique to render
btop-style gradient bar meters and sparklines in an always-visible Plasma
panel widget that redraws every 1-2s?

Target: Plasma 6.7.5, Qt 6.11.2, QML.

## 1. Rendering technique comparison

| Technique | What it is | Cost model | Verdict |
|---|---|---|---|
| `Canvas` (QML 2D canvas) | Immediate-mode JS drawing API (`getContext("2d")`), backed by a `QImage` or FBO the size of the item, re-rasterized on `requestPaint()`. | Only costs CPU/GPU when `requestPaint()` is actually called — idle between paints costs ~nothing. Cost scales with canvas *pixel area* and drawing complexity, not with scene complexity elsewhere. | **Recommended for both bar meters and sparklines.** This is what real-world reference projects (see §5) use exclusively, for exactly this use case. |
| `QtQuick.Shapes` | Declarative vector shapes (`ShapePath`, `PathLine`, etc.), GPU-tessellated and cached as scenegraph geometry, re-tessellated only when the path geometry actually changes. | Very cheap for *static* shapes (tessellation happens once, then it's just a textured quad the compositor reuses each frame). Gets *expensive* for a shape whose path changes every update (a scrolling sparkline's path changes every tick), because Qt Quick has to redo CPU-side tessellation each time the geometry changes — historically slower than Canvas for this specific case per the Qt Shape-vs-Canvas forum thread. | Good fit for *static or rarely-changing* decorative shapes (rounded bar outlines, icons) but not the primary choice for data that mutates every tick. |
| Stacked `Rectangle`s with `gradient`/`GradientStop`, width bound to value | Pure declarative items; the scenegraph batches/caches these as simple textured quads and only repaints the pixels that actually change (the fill width). | Cheapest possible option — no rasterization step at all, scenegraph handles it like any other UI element, GPU-composited, near-zero CPU cost per update. | **Recommended for the solid gradient bar meter** (CPU/mem/GPU/VRAM % bars) — no reason to use Canvas for a single rectangle whose width and gradient stops change. |
| `QtQuick.Controls` `ProgressBar` + custom style | Standard control, restyled via `contentItem`/`background` delegates. | Same underlying cost as Rectangles once restyled, but drags in Controls styling machinery/theming overhead and fights the "btop look" (control internals assume a generic progress-bar visual/interaction model). | Not recommended — restyling it is more work than just building a 2-3 `Rectangle` bar component from scratch, for no benefit. |
| Qt Quick `Charts`/`Graphs` module | `QtCharts` is **deprecated as of Qt 6.10** (present in 6.11 but obsolete/on the way out); `QtGraphs` is its replacement, available in Qt 6.11.2, and its 2D backend is itself implemented on top of `QtQuick.Shapes`. | Full charting framework — axes, legends, multiple series types, theming — architecturally heavier than needed for a single trend line in a small panel widget; adds a module dependency and QML import surface just to draw one sparkline. | Not recommended for this project. Overkill for panel-widget sparklines; the two reference implementations found (§5) don't use it either. Worth reconsidering only if a future story needs multi-series charts with legends/axes/tooltips in a popup detail view. |

**Recommendation:**
- **(a) Solid gradient bar meter** (CPU/mem/GPU/VRAM/disk %, single value 0-100%): use a **stacked-`Rectangle` component** — one background track `Rectangle` plus one fill `Rectangle` whose `width` is bound to the value and whose `gradient` is computed live (see §2). This is the cheapest option and needs no imperative drawing code at all.
- **(b) Scrolling sparkline / history graph** (net throughput, GPU utilization trend, etc.): use **`Canvas`**, repainted only via an explicit `requestPaint()` call when new data arrives (data-driven, *not* a frame-rate timer) — never bind `onPaint` to be re-triggered by continuous animation. Both real-world reference plasmoids found in this spike (§5) independently converge on exactly this pattern (Canvas + `onValuesChanged: requestPaint()`), which is a strong signal it's the pragmatic default for this exact use case.

Rationale specific to "sits in the panel all day": a 1-2s poll interval means the *steady-state* cost of either approach is dominated by how often something actually repaints, not by theoretical peak throughput — so the deciding factor is avoiding idle cost and avoiding wasted repaints, which both Rectangle-binding and data-driven Canvas satisfy. Shapes' cost profile is backwards for a scrolling graph (cheap when idle, expensive exactly when the data — i.e. every tick — changes), which is why it's not the pick for (b) despite being GPU-composited.

## 2. Color/gradient threshold technique (btop green→yellow→red)

Two workable QML-native approaches, no shaders required:

1. **Multi-stop `Gradient` on the fill `Rectangle`, stops computed from the current value.** Declare `gradient: Gradient { GradientStop { position: 0.0; color: ... } ... }` and recompute stop positions/colors in a JS function bound to the value, e.g. clamp stops so the color ramp (green → yellow ~50% → red ~80%+) is always visible across the *filled* portion of the bar, not the whole track — this reproduces btop's smooth gradient-along-the-bar look rather than a hard cutoff. Since `GradientStop` objects are QML objects, they can be created once as named children and have `.position`/`.color` updated imperatively from a value-changed handler, avoiding tearing down and rebuilding the `Gradient` object every tick.
2. **Precomputed color ramp function returning a single interpolated color**, used either as a flat `fillColor` for the whole bar (simplest, hard-edged-per-update but smooth over time as the value walks the ramp) or as one end of a two-stop gradient anchored to the current threshold color with the other stop as a darker/lighter shade of the same color (cheap way to keep the "chunky gradient" look without needing 3 literal color stops). `Qt.rgba()`/manual linear interpolation between the three threshold anchor colors (green/yellow/red) in a shared JS helper in `shared/theme/` (e.g. `ColorScale.js` or a `ColorScale` QML singleton) keeps this logic in one place for all five widgets, per the project's shared-component requirement.

No shader effort (`ShaderEffect`) is warranted here — gradients driven by plain QML `Gradient`/`GradientStop` bindings are already GPU-composited by the scenegraph and are the idiomatic, lowest-effort way to hit this look. Reserve shaders for a future "glow"/CRT-scanline polish pass if the product owner wants that later, not for basic threshold coloring.

**Recommendation:** put a single `ColorScale` component/singleton in `shared/theme/` with a `colorForValue(value, max)` function (and named threshold properties: `goodMax: 0.5`, `warnMax: 0.8` or similar) returning either a color or a ready-made 3-stop `Gradient`-stop array, consumed by both the bar meter and sparkline components so all five widgets agree on what "yellow" means.

## 3. Font

- **Recommended family: a monospace font, matching the terminal-dashboard reference.** The two closest real-world reference plasmoids (§5) both default to a generic/system monospace: knvtop uses the QML generic alias `font.family: "monospace"` for numeric readouts; konky exposes a user-configurable `fontFamily` defaulting to `"Noto Mono"`, with `"monospace"` used as the raw fallback in its config UI preview. Neither bundles a custom font file.
- **Loading approach:** for a *system* font (default path), just set `font.family` on `Text` items — no `FontLoader` needed, KDE/Fedora ships Noto Mono and DejaVu Sans Mono by default, and the generic `"monospace"` family alias resolves via Qt's fontconfig integration to whatever the user's system default monospace font is, which also respects the user's own font preferences (accessibility-friendly, no license bundling burden).
- **Bundling a font (e.g. JetBrains Mono or a Nerd Font) is technically feasible but not necessary or recommended as the default:** QML's `FontLoader { source: "qrc:/fonts/..." }` (or, in plasmoid packaging terms, a file under `contents/ui/fonts/` referenced by relative path/`Qt.resolvedUrl()`) works fine at runtime cost of loading the font file once at startup; the practical blockers are (a) font licensing — JetBrains Mono (Apache 2.0) and most Nerd Fonts (SIL OFL) are redistribution-friendly, so licensing isn't actually a blocker if the product owner wants a bundled look guarantee, but (b) it adds package size and a font-loading failure mode, and (c) neither reference project bothered, suggesting the visual payoff isn't worth it for this style of widget (chunky bars carry the "terminal" look; the numeric text just needs to be tabular/monospaced so digits don't jitter width as values change).
- **Recommendation:** default to `font.family: "monospace"` (or a small ordered fallback list, e.g. `["JetBrains Mono", "Noto Sans Mono", "monospace"]`, letting Qt pick whichever resolves) with a numeric readout style that fixes digit width behavior (`font.family` generic monospace already guarantees this) — and leave bundling a specific font as a nice-to-have config option (`shared/theme/` exposes a `fontFamily` property, configurable per-widget like konky does) rather than a hard dependency, revisited only if the product owner specifically wants a guaranteed-identical look regardless of the user's installed fonts.

## 4. Performance guidance / pitfalls

- **The single biggest documented pitfall is repainting on a fixed timer/animation loop instead of on data change.** Community reports (Qt Forum, Arch Linux forums) describe QML `Canvas` + `Timer`-driven `requestPaint()` causing measurable animation/performance problems, and a widget stuck redrawing continuously "for zero benefit" draining laptop battery even while the panel item is collapsed/not visually changing. **plasmatop's poll interval (1-2s) means this risk is structural if not guarded against** — never wire Canvas repaint to a `NumberAnimation`/frame-synced loop; only call `requestPaint()` from the same handler that receives fresh data (`onValuesChanged`, or the data-source's update signal directly). Both real-world reference plasmoids (§5) follow exactly this pattern.
- **Canvas repaint cost scales with canvas pixel area and draw-call complexity, not with how often you *could* repaint** — keep sparkline/graph `Canvas` items small (reference projects use ~40×20px to ~100×40px for panel sparklines) and avoid full-window-sized canvases for panel-embedded meters.
- **`ctx.reset()` (or `clearRect`) at the top of `onPaint` is standard and cheap** — Canvas does not auto-clear between paints, so all reference code explicitly resets the context; skipping this causes visible trail/ghosting artifacts, not a performance win, so don't try to "optimize" it away.
- **`renderTarget`/`renderStrategy`:** `Canvas.FramebufferObject` (GPU-backed FBO) is generally faster than the default `Canvas.Image` (CPU-side `QImage`) render target when hardware acceleration is available, per Qt's own Canvas docs guidance; for small panel-widget canvases redrawn once per poll tick the difference is unlikely to be perceptible either way, but it's a one-line property to set (`renderTarget: Canvas.FramebufferObject`) and costs nothing to enable proactively. `Canvas.Cooperative`/`Canvas.Threaded` render strategy (background-thread rendering) matters for *long-running* paint operations — not relevant at this widget's drawing complexity (a filled path + stroke + small amount of text), so leave it at the default.
- **Prefer declarative property bindings (Rectangle width/gradient) over Canvas wherever the shape genuinely is just a rectangle** — every pixel drawn via `Canvas` costs a rasterization pass that a bound `Rectangle` property change does not; this is the core reason bar meters (§1a) should not be Canvas at all.
- **Visibility/collapse awareness:** one documented real-world fix for a Plasma widget's battery-drain complaint was binding timer interval/repaint cadence to whether the widget is actually visible/expanded (e.g. throttling a fast update loop to 1s when collapsed in the panel vs. faster when the popup is open). plasmatop's baseline 1-2s interval is already conservative, but if a future "detail popup" view wants a snappier refresh when open, gate the *faster* interval to popup-visible state rather than always polling fast.
- **Avoid recreating JS objects/arrays every paint where avoidable** (e.g. don't rebuild a full gradient object from scratch every single frame if only the value changed and stops can be mutated in place) — minor GC-pressure concern at this update frequency (1-2s) but essentially free to just do right from the start using the named-`GradientStop`-mutation pattern in §2.

## 5. Existing open-source reference projects (cloned and inspected for this spike)

1. **knvtop** — <https://github.com/DAE51D/knvtop> — KDE Plasma 6 widget, nvtop-style GPU (+ LLM process) monitor for the panel. Directly relevant: multi-line compact panel graph expanding to a popup with per-metric rings and sparklines, deliberately built for Intel/AMD/NVIDIA GPU telemetry in the panel — closest existing analog to `plasmatop-gpu`'s intended UX. Its `Sparkline.qml` and `Ring.qml` (both `Canvas`-based, `requestPaint()` called only from property-changed handlers, never a timer) are usable directly as a starting reference for `shared/theme/`'s sparkline component; numeric readouts use `font.family: "monospace"`, no bundled font.
2. **konky** — <https://github.com/asvanyviz/konky> — KDE Plasma 6 widget explicitly described as bringing "Conky philosophy" (declarative, JSON-module-configured, terminal-dashboard-style system stats) to Plasma, built on KSystemStats/Kirigami/Plasma6 APIs. Has a full `charts/` component set (`ChartBar.qml`, `ChartSparkline.qml`, `ChartLine.qml`, `ChartRing.qml`) all implemented as `Canvas` items with gradient fills (`createLinearGradient`) and a `pushValue()`/rolling-array history pattern directly analogous to what `plasmatop-net`/`plasmatop-disk` sparklines will need. Font is user-configurable (`fontFamily`, default `"Noto Mono"`), no bundled font file. Poll interval is a configurable `Timer` defaulting in the ~1s range, matching plasmatop's target cadence.

Both are non-store-published-verified-safe to browse/clone for reference but should be treated as **inspiration/pattern reference, not code to copy wholesale** (different licenses/authors) — reimplement the patterns (Canvas + data-driven `requestPaint()`, rolling-array history, linear-gradient fills, monospace system font) fresh in `shared/theme/`.

## Summary recommendation for `shared/theme/` (feeds into ARCHITECTURE.md)

- `BarMeter.qml` — stacked `Rectangle`s (track + value-bound fill), gradient stops driven by `ColorScale`, no Canvas.
- `Sparkline.qml` — `Canvas`, rolling value array, `requestPaint()` called only from the data-update path, small fixed pixel size, `renderTarget: Canvas.FramebufferObject`.
- `ColorScale.qml` (singleton or plain component) — shared `colorForValue()`/gradient-stop-array helper implementing green(<~50%)→yellow(~50-80%)→red(>~80%) with smooth interpolation, consumed by both of the above.
- Font: `font.family` fallback list ending in generic `"monospace"`, configurable per-widget; no bundled font file for v1.
